**Requirements:**

- **Test Scenarios:** Create test cases covering happy path, error cases, edge cases, boundary conditions, and integration failure scenarios. Each scenario must have a unique ID and clearly map to a specific validation point in the flow.

- **Test Data:** Provide realistic, production-like payloads for each scenario type. Include valid XML/JSON structures that the iFlow expects, plus malformed and edge-case variations.

- **Pytest Script:** Write fully executable Python code that:
  - Imports `requests`, `pytest`, `json`, `xml.etree.ElementTree`
  - **NEVER performs real network I/O.** The CI runner has no access to internal
    SAP hosts, and a connection attempt must be treated as a defect - never
    hidden behind `pytest.skip` or marked flaky.
  - Chooses ONE mocking strategy and applies it consistently:
    - preferred: the `responses` library (`@responses.activate` + `responses.add(...)`), OR
    - stdlib `unittest.mock.patch` - and when patching, patch **every** call path
      actually used. `requests.post` and `requests.Session().post` are DIFFERENT
      targets: patching one does not intercept the other. If the code under test
      uses a session, patch the session method or mock the whole session object.
  - Uses an **ephemeral port** for any local mock server (`port=0`, or a port read
    from an environment variable). Two suites in the same run must never depend
    on the same fixed port.
  - Never hardcodes an internal hostname or a real endpoint. Use documentation
    addresses (`example.invalid`, `localhost`) for anything appearing in a URL.
  - Asserts on `headers` and `properties` of the message wherever possible, so the
    test checks real outcomes. Do **NOT** write a Python re-implementation of a
    Groovy script as a substitute for exercising it: the Groovy scripts are
    executed separately by the CI harness, and a Python copy of the logic tests
    nothing.
  - Uses fixtures for test data setup
  - Includes assertions that validate both response structure and business logic outcomes
  - Handles timeouts, connection errors, and partial failures gracefully

- **Risk Analysis:** Identify risks specific to this integration (data loss, transformation errors, connection failures, timeout scenarios, etc.). For each risk, describe the business consequence and the mitigation strategy your tests cover.

- **Coverage Analysis:** Calculate the percentage of flow logic covered by your test suite. Break down coverage by component (mappings, conditions, routing, error handlers). For any paths not covered, explain why and recommend specific test scenarios to reach 100%. The goal is 100% coverage.
